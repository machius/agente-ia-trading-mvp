# AI Trading Agent

An open-source AI-powered financial market analysis platform designed to combine quantitative analysis, technical indicators, machine learning, market sentiment, macroeconomic data, geopolitical context, and an AI agent into a single modular system.

The primary goal of the project is to provide **interpretable, traceable, and data-driven market analysis** rather than autonomous trading.

> **Project status:** Early development / MVP
> **Initial assets:** S&P 500 and Gold
> **Primary language:** Python 3.11+
> **Execution:** Analysis and paper-trading oriented; no autonomous live trading in the initial version

## Overview

The AI Trading Agent is a modular platform for analyzing financial markets using a combination of deterministic quantitative models, machine learning, external financial information, and large language models (LLMs).

The system is designed around an important principle:

> **The LLM is an interpretation and interaction layer, not the source of financial truth.**

Quantitative calculations, indicators, predictions, probabilities, and risk metrics must be generated by deterministic or statistically validated components whenever possible.

The AI agent consumes those results and uses them to:

* Explain market conditions.
* Interpret quantitative signals.
* Analyze external information.
* Compare assets.
* Generate reports.
* Answer user questions.
* Provide contextual explanations.
* Create informative alerts.

The initial version will not execute real trades autonomously.

# Architecture

The platform follows a modular architecture with five primary layers.

```text
┌──────────────────────────────────────────────┐
│                  User Interface               │
│             Streamlit / React                │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│                 AI Agent Layer                │
│              LangGraph + LLM                 │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│                 Signal Engine                 │
│       Rules + ML Models + Risk Engine        │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│             Quantitative Processing           │
│ Indicators + Features + Statistics + ML     │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│                 Data Layer                   │
│ Market + News + Macro + Sentiment + DB       │
└──────────────────────────────────────────────┘
```

# Signal Engine

The signal engine combines quantitative indicators, machine-learning outputs, sentiment, and contextual information.

Initial signal categories:

| Signal           | Description                                      |
| ---------------- | ------------------------------------------------ |
| `POTENTIAL_BUY`  | Conditions potentially favor an upward scenario  |
| `HOLD_WAIT`      | Conditions do not justify a directional signal   |
| `POTENTIAL_SELL` | Conditions potentially favor a downward scenario |
| `HIGH_RISK`      | Market conditions indicate elevated risk         |
| `NEUTRAL`        | No significant directional bias detected         |

Each generated signal should contain:

```text
Asset
Timestamp
Current Price
Indicators
Detected Conditions
Risk Level
Confidence Level
Positive Factors
Negative Factors
Expected Scenario
Invalidation Conditions
```

Signals must be explainable and traceable to the underlying data and models.

# Scenario Analysis

The system should generate multiple possible scenarios rather than a single deterministic prediction.

Example:

```text
Bullish Scenario
Probability: 60%

Conditions:
- Price above 50-session moving average.
- Price above 200-session moving average.
- Increasing volume.
- Favorable sentiment.
```

```text
Neutral Scenario
Probability: 25%

Conditions:
- Momentum deterioration.
- Low volatility.
```

```text
Bearish Scenario
Probability: 15%

Conditions:
- Support breakdown.
- Increasing volatility.
- Deteriorating sentiment.
```

Probabilities must originate from quantitatively evaluated models.

The LLM must not fabricate probabilities.

# Backtesting

A backtesting module is required before using the system for real-world alerts.

The backtesting framework should support:

* Historical strategy simulation.
* Strategy comparison.
* Return calculation.
* Drawdown calculation.
* Volatility calculation.
* Sharpe Ratio.
* Sortino Ratio.
* Win rate.
* Risk/reward analysis.
* Benchmark comparison.

The implementation must explicitly protect against:

* Data leakage.
* Look-ahead bias.
* Survivorship bias where applicable.

Data should be separated chronologically:

```text
Training
    │
    ▼
Validation
    │
    ▼
Testing
```

The final evaluation must use data that was not available to the model during training.

# Development Principles

The project should follow several core principles.

## 1. Quantitative Models First

Financial calculations should be performed by deterministic mathematical or statistical components rather than by the LLM.

## 2. LLM as an Interpretation Layer

The LLM should interpret validated information rather than generate unsupported financial facts.

## 3. Traceability

Every signal should be traceable to:

```text
Data
  ↓
Indicators
  ↓
Features
  ↓
Model
  ↓
Probability
  ↓
Signal
  ↓
Explanation
```

## 4. Reproducibility

A signal should be reproducible using the same data, model version, parameters, and configuration.

## 5. Probabilistic Reasoning

Predictions should be expressed as probabilities and scenarios rather than certainties.

## 6. Separation of Responsibilities

The architecture should maintain a clear separation between:

```text
Data
→ Analysis
→ Prediction
→ Risk
→ Signal
→ Recommendation
→ Execution
```

## 7. No Autonomous Trading by Default

Live trading capabilities must not be enabled by default.

# Model Evaluation

A model should not be considered useful solely because it performs well on historical data.

Evaluation should consider:

* Out-of-sample performance.
* Walk-forward validation.
* Backtesting.
* Probability calibration.
* Drawdown.
* Volatility.
* Sharpe Ratio.
* Sortino Ratio.
* Risk/reward ratio.
* False-positive rate.
* Stability across market regimes.

Where applicable, models should be tested across different market conditions, including:

* Bull markets.
* Bear markets.
* High-volatility periods.
* Low-volatility periods.
* Significant macroeconomic events.

# Limitations and Disclaimer

This project is intended for **research, financial analysis, experimentation, and decision support**.

It is not intended to guarantee financial returns or provide personalized financial advice.

Historical performance does not guarantee future results.

No prediction should be interpreted as a certainty. Market conditions can change unexpectedly, and quantitative models may fail under conditions that differ from those observed during training or backtesting.

Before considering the use of any strategy with real capital, it should undergo:

1. Historical backtesting.
2. Out-of-sample validation.
3. Paper trading.
4. Risk analysis.
5. Stability testing.

The project should prioritize transparency and traceability so that users can understand which data, indicators, models, and external information contributed to each generated signal.

---

# Design Philosophy

The project is based on a simple principle:

> **Build a quantitative financial system first, then place an AI agent on top of it.**

The AI agent should not replace quantitative analysis.

Instead, it should make the quantitative system easier to interact with, understand, monitor, and extend.

The intended architecture is:

```text
Reliable Data
      ↓
Quantitative Analysis
      ↓
Validated Models
      ↓
Risk Assessment
      ↓
Signal Generation
      ↓
Scenario Analysis
      ↓
AI Interpretation
      ↓
Human Decision
```

The final decision remains with the human user.
